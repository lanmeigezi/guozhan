# AI 调用成本控制指南

> 阶段四交付物 · 2026-10-24
> 本文所有 token 数字均为**本机实测**（`tools/measure-prompt.ts` 跑出，命令见 §6.5，可随时复现），不是估算。
> 单价部分标注为**假设值**——请以 provider 官方定价页为准，本文给的是公式与敏感性表，改单价即可重算。

---

## 0. 一句话结论

**一局 40 回合的国战，LLM 成本约 ¥1.4 – ¥3.7**（DeepSeek 档位单价假设下），
且这个数字**不会因为 LLM 变慢或挂掉而影响游戏**——回合结算是纯确定性代码，毫秒级完成，从不等 LLM。

成本可控的三个结构性原因，都不是"少调用"这种消极手段：

1. **只有 3/7 个席位走 LLM**，次级国家走启发式代码（§1.2）
2. **提示词经过四层压缩**，态势文本比直接发 JSON 快照省 **约 72%**（§2，实测 8893 → 2515 字符，同一份态势）
3. **数值全由代码算**，LLM 不需要看精确数字，只看分层标签（§2.3）

## 1. LLM 调用频率

### 1.1 触发条件（P12：事件唤醒，不由时钟驱动）

| 触发器 | 何时 | 频率 | 是否阻塞回合 |
|---|---|---|---|
| **回合边界**（主） | 每回合结算完成后，为**AI 席位**（`kind=ai`）自动生成下一回合建议；人类席位（军师模式）**按需**请求，不自动调用 | 每回合 × AI 席位数 | ❌ 不阻塞 |
| **玩家显式询问**（交互） | 人类在酒馆点"问军师" | 按需 | ❌ 不阻塞 |
| **规则状态机跃迁**（急） | `peaceful→engaged→critical`，跃迁时提升优先级插队 | 罕见 | ❌ 不阻塞 |
| **叙事生成** | 结算后异步流式补发 | 每回合 × 需叙事的席位数 | ❌ 不阻塞 |

**刻意不做的**：不做"每 N 秒轮询一次 LLM"。OpenRA-RL 的数据说明时间推进应该由引擎负责——它的 `advance` 工具占全部调用的 **57%**，是 LLM 主动批量跳过空闲时段。我们是回合制，天然没有空转 tick，连这个大头都省了。

### 1.2 分级策略：只有 3/7 席位走 LLM ★最大的省钱杠杆

来自 Histrategy 的实测经验，它对次要势力（刘表/刘璋）走启发式，理由写在代码 docstring 里：
> "Reason: reduce token cost and prevent behavior from deviating from history"

本项目在 `config/scenarios/warring-states/scenario.json` 里声明：

```json
"seats": {
  "majorAi": ["qin", "zhao", "chu"],              // 走 LLM
  "minorAi": ["wei", "han", "yan", "qi"]          // 走 src/ai/heuristic.ts，零 token
}
```

**直接省掉 4/7 ≈ 57% 的顾问调用。** 而且次级国家的行为更稳定（不会因为模型换了就性格大变）。

`src/ai/heuristic.ts` 的四档 profile（`cautious` / `balanced` / `aggressive` / `desperate`）按势力的 `aggression` 与领土数自动选档。**它同时是 LLM 彻底不可用时的全局降级路径**——没有 key、超时、预算耗尽，游戏都能继续。

### 1.3 单飞与在途合并（防重复调用）

`src/ai/advisor.ts` 的 `AiAdvisor.request()`：

- **每席位单飞**：同时只有一个 LLM 请求在途。在途期间的第二次请求**返回同一个 Promise**，不会发起新调用。
- **在途合并**：新态势覆盖旧的（过期态势丢弃），但**人类留言全部累积不丢**。
  这是 OpenArma `merge_situations` 的语义：*"态势取最新可丢、human_messages 一条不丢"*。
- 最多两轮（首请求 + 一次堆积合并），不会无限循环。

实测由 `tests/deterministic/ai-layer.test.ts` 的 `★ 单飞：并发两次请求只触发一次 LLM 调用` 守着。

## 2. Token 上限

### 2.1 实测提示词体积（本机跑出，不是估算）

| 组成 | 字符数 | ≈ tokens（中文按 chars/2） |
|---|---|---|
| 系统提示词（角色+剧本+五类纪律+schema） | 1740 | **870** |
| 态势文本（动作清单 ≤24 条） | 2515 | **1258** |
| ├─ 其中地图拓扑文本 | 514 | 257 |
| **单次顾问调用输入合计** | 4255 | **≈ 2128** |

对比：**直接把 JSON 快照发给 LLM 是 8893 字符**，同一份态势文本渲染后 2515 字符 —— **省约 72%**（系统提示词两种方式都要发，不参与这个比值）。
这就是 P13「四层压缩」的实际收益。

### 2.2 max_tokens 分级（照 Histrategy 的做法）

| 用途 | max_tokens | 理由 |
|---|---|---|
| `advisor`（战略建议） | **2048** | 输出是结构化 JSON，6 条建议 + 外交辞令足够 |
| `narrative`（叙事） | **1024** | 纯文本，且移出关键路径 |
| `intent_parse`（自然语言→命令） | **512** | 只输出命令数组 |
| ❌ 反面教材 | ~~16384~~ | Histrategy V1 用的值，已随 V1 一起下线 |

另外在提示词里写死**字符硬限**（Histrategy 的做法："总输出不得超过 2000 字符，超过则视为失败"），
以及 `renderSituation(snap, { maxSituationChars: 6000 })` 的**输入侧截断**（超出则从动作清单尾部截，并显式标注"已达上限"，不静默）。

### 2.3 ★给 LLM 看标签，不给精确数值

这条同时省 token **和**降幻觉，是双赢：

| 不给 | 给 | 出处 |
|---|---|---|
| 齐国国库 4000 金 | `财:充裕` | `src/core/labels.ts` 的 `GOLD_TIER_LABELS` |
| 兵力 18000 | `野戰軍` | `ARMY_TIER_LABELS` |
| 人口 183,421 | `发展度:中等` | `DEVELOPMENT_LABELS`（离散 1-5 级） |
| 敌方精确编制 | `partial` 可见性下的档位 | `src/core/projection.ts` |

依据是 Histrategy `docs/design/state-complexity-vs-llm-hallucination.md` 对 CK3 / Total War / Civ VI 的调研结论：

> 1. 越成功的策略游戏，数值变量的**独立维度越少**（CK3 只有"发展度"一个宏观指标）
> 2. **离散 > 连续** ——「3 级城池」比「人口 183,421」更稳健
> 3. **LLM 调参数，代码算结果**

它们的 V1 让 LLM 直接看精确数值，结果孙权人口被推演成 **18.3 万**（史实约 200 万）。

**己方是唯一给精确数值的**（`snapshot.factions[].exact`），因为玩家需要真实数字做决策；
他国一律只给档位 —— 这同时是战争迷雾的要求（实测秦国视野：4 full / 3 partial / 12 name_only）。

## 3. 廉价模型推荐

| 档位 | 适用 | 说明 |
|---|---|---|
| **DeepSeek-V3 / deepseek-chat** ★推荐默认 | advisor + narrative | OpenAI 兼容、中文强、单价低。本项目 `scenario.json` 与 `.env.example` 的默认值 |
| DeepSeek-R1 / reasoner | 只在"复杂外交斡旋"场景按需启用 | 推理模型单价高数倍，且慢；国战的战术判断不需要长链推理 |
| 各类 flash / mini 档 | narrative（纯叙事） | 叙事是"可以夸张"的 Layer 3（P1），用小模型完全够 |
| 本地 Ollama（Qwen3-32B 等） | 离线/隐私场景 | ⚠️ 见下方警告 |

### ★一条来自实测的警告：小模型会"只种田不打仗"

OpenRA-RL 用 Ollama 本地 Qwen3-32B 打红警 Beginner AI，5 局结果：

```
economy 0.58–0.80 ✅   infrastructure 高 ✅   combat = 0 ❌   disruption = 0 ❌
5 局全部时间到平局，零次战斗交锋
```

官方复盘：*"prompt-driven LLMs do not yet capture"* 长链条军事规划；
*"In-context reflection helps, but is not enough… **Prompt-injection learning fixes build order — it does not close the combat gap.**"*
（局后反思确实修好了建造顺序——第 2 局诊断出"战争工厂应排在发电厂后"，第 4 局开局计划就改了——但 combat=0 纹丝不动。）

**根因**：系统提示词里有 `Build economy early, army later` 这类**软性阶段描述**，被 32B 模型执行成了"永远经济"。

### 本项目的三重对策（都是硬约束，不指望模型自觉）

1. **硬性回合里程碑**（`scenario.json` 的 `milestones`，代码校验，未达成即告警+扣分）：
   ```json
   { "turn": 6,  "require": { "offensiveArmies": 2 }, "message": "第 6 回合前必须编成至少 2 支可进攻的野战军" }
   { "turn": 14, "require": { "attacksLaunched": 1 },  "message": "第 14 回合前必须发起至少 1 次进攻" }
   { "turn": 24, "require": { "regionsCaptured": 1 },  "message": "第 24 回合前必须夺取至少 1 个敌方区域" }
   ```
2. **"该做没做"型告警**（`config/rules/alerts.json`）：`turns_since_recruit_at_least` / `turns_since_attack_at_least`。
   ★OpenRA-RL 的 `IDLE ARMY` 告警**只统计已存在的部队**，AI 根本没造兵时告警无从触发 —— 这是它的盲区，我们补上了。
3. **提示词里明写反拖延措辞**（`src/ai/prompt-render.ts`）：
   > 「这类目标**不能用"先发展经济，日后再说"来推迟**。发展本身不是目的，达成目标才是。」

启发式路径（次级国家）更彻底：`decideHeuristic()` 里**里程碑逼迫时即使没有优势目标也会出击**，
门槛从 `attackRatio` 降到 0.9，一个都不达标就打最强的那个。规则代码不会有"性格问题"。

## 4. 异步非阻塞：如何不影响游戏主循环

### 4.1 铁律：结算绝不等 LLM

这是 Histrategy 用 60-100s 延迟换来的教训。它的 V1 实测：

> **User-facing latency: 60-100s** for a 3-faction scenario. With timeout+retry, worst case is 260s.
> | Zero visibility | User stares at spinner for 100s |
> | Single point of failure | One bad JSON parse → entire turn wasted |
> | Retry = double pain | Timeout at 130s → retry → 260s total |

诊断结论原文：
> **State computation** | Arithmetic/logic | Needs thinking? **No** | Can be parallel? Yes
> **Narrative generation** | Creative writing | Needs thinking? Yes | Can be parallel? No
> The fundamental insight: **you can play the game knowing only the state numbers. The narrative is flavor that can arrive later.**

修复后：Time-to-playable **60-100s → <2s**，成功率 ~80% → >95%。

### 4.2 本项目的实现（代码位置）

```
phase = submitting        人类思考 / AI 后台生成建议（不阻塞任何人）
        ↓  收齐或超时（human 300s / ai 120s）
phase = resolving         ★纯确定性，毫秒级，同步
                          resolveTurn(state, world, modules, orders, llmDelta?)
                          · llmDelta 是**已经备好**的；没备好就传 undefined
                          · 本回合按纯确定性走，建议顺延为下一回合输入
                          · 实测 <50ms/回合（tests/deterministic/replay.test.ts 有性能闸门）
        ↓  立即推 WS `settled` 事件（含全部数值）
phase = narrating         异步流式补发叙事，失败→模板兜底
                          "Phase 2 failure doesn't block the next turn"
        ↓
phase = submitting (t+1)  后台预生成下一回合 AI 决策
                          ★与人类思考时间重叠（Histrategy 靠这个省 30-40s）
```

关键点：
- **LLM 完全不在数据通路上**。`src/core/` 零 IO、零网络（`tools/arch-check.ts` 机器强制，违规即 CI 红）
- **fire-and-forget**：房间层调 `advisor.request()` 不 await，结算照跑
- **超时不重试到死**：`LlmClient` 只对 408/425/429/5xx 与网络错误指数退避（最多 2 次），400/401/403 立刻放弃——对鉴权错误重试只是烧钱
- **LLM 挂了游戏照玩**：`advisor` 降级 `heuristic`，`resolveTurn` 收 `undefined` 走纯确定性

### 4.3 并发限制（1-2 核机器）

- LLM HTTP 请求用信号量限并发 **2-3**（更多会饿死事件循环）
- Node 单进程事件循环 + `node:sqlite` 同步 API：确定性核心是纯 CPU 毫秒级，IO 全在房间层串行
- 实测资源预估：**10+ 房间 RSS 150-200MB**，1 核 2GB 可稳定跑

## 5. 单局成本预估

### 5.1 实测 token 基数

| 项 | 输入 tokens | 输出 tokens |
|---|---|---|
| advisor 单次 | **2128**（实测） | ≤2048，典型 **~500** |
| narrative 单次 | ~800（事实清单，比态势短） | ≤1024，典型 **~400** |

### 5.2 两种典型配置

**配置 A：3 个 LLM 席位 + 每回合 2 次叙事（推荐默认）**

```
每回合 = 3 × (2128 + 500) + 2 × (800 + 400) = 7884 + 2400 = 10284 tokens
40 回合 = 414,120 tokens
  输入 322,000  ·  输出 92,000
```

**配置 B：7 个席位全走 LLM + 每回合 7 次叙事（最贵）**

```
每回合 = 7 × 2651 + 7 × 1200 = 18557 + 8400 = 26957 tokens
40 回合 = 1,078,280 tokens
  输入 826,000  ·  输出 252,000
```

### 5.3 成本敏感性表

⚠️ **下表单价是假设值，请以 provider 官方定价页为准**。公式：
`成本 = 输入tokens/1e6 × 输入单价 + 输出tokens/1e6 × 输出单价`

| 单价档（¥/百万 tokens） | 配置 A（3 席） | 配置 B（7 席） |
|---|---|---|
| 输入 ¥1 / 输出 ¥2（flash 档） | **¥0.51** | ¥1.33 |
| 输入 ¥2 / 输出 ¥8（DeepSeek-chat 档，本文基准） | **¥1.38** | ¥3.67 |
| 输入 ¥4 / 输出 ¥16 | ¥2.76 | ¥7.33 |
| 输入 ¥15 / 输出 ¥60（旗舰档） | ¥10.35 | ¥27.50 |

**结论：用 DeepSeek 档位，一局 40 回合约 ¥1.4（3 席）到 ¥3.7（7 席全 LLM）。**

### 5.4 与 Histrategy 实测数据的交叉校验

它们的自报成本口径（`docs/design-iterations.md` / `design-v3 §7`）：

| 它们的口径 | 数值 |
|---|---|
| V1 时代（纯 LLM 全量推演） | 2000-4000 tokens/turn ≈ ¥0.0004/回合，100 回合 < ¥0.05 |
| v2（纯确定性） | ~$0.02/turn |
| v3（混合，默认） | ~$0.06/turn |
| 文件式状态 | ~2,600 tokens/turn → $0.002/turn |
| 玩家容忍上限 | ~$0.05/turn |
| **被否决的方案** | "Full LLM agent loops for NPCs are too expensive (**~$0.10/NPC/turn**) and inconsistent. Stateful profiles + LLM interpretation gives **80% of the drama at 5% of the cost**." |

我们的 2128 tokens/次输入与它们的 "~2,600 tokens/turn" 同一量级，说明压缩做到了行业水平。
配置 A 折合 **~$0.027/回合**，低于它们 v3 的 $0.06，也远低于 $0.05 的玩家容忍线。

它们否决"每个 NPC 都跑完整 agent loop"的理由（$0.10/NPC/turn）正是我们 §1.2 分级策略的依据 ——
**"状态化人设 + LLM 解读"能用 5% 的成本拿到 80% 的戏剧性**。

### 5.5 ★成本从来不是 V1 的死因

必须强调这点，否则容易得出错误结论：

Histrategy V1 的成本是 **¥0.0004/回合**，便宜到可以忽略。它 2026-10-03 被下线，
死因是**幻觉、偏向玩家、不可复现、60-100s 延迟**，不是贵。

> **不要以为"token 便宜就能让 LLM 算数值"。**

本项目的"禁止 LLM 参与数值计算"是**正确性约束**，不是成本约束。即使 LLM 免费，这条也不该松。

## 6. 预算闸与降级（Histrategy 缺的一环）

Histrategy 只有**事后记账**（`llm_call_log` 表），没有**事前预算闸**。我们补上了：

### 6.1 三层预算

```json
// scenario.json
"budget": {
  "perSeatTokenCap": 200000,     // 席位级累计上限
  "perTurnCallCap": 8,           // 单回合调用次数上限
  "onExceed": "degrade_to_deterministic"   // ★降级，不是中断
}
```

### 6.2 闸门前置（★关键实现细节）

`src/ai/advisor.ts` 的 `runOnce()` 里，预算检查在**发起 HTTP 请求之前**：

```
if (llmDriven && tokenUsed >= tokenCap) {
  记一条 status='budget_exceeded' 的账  →  降级 heuristic  →  return
}
```

由 `tests/deterministic/ai-layer.test.ts` 的 `★ token 预算耗尽 ⇒ 不调 LLM` 守着，
断言里明写：*"预算耗尽必须在**发请求之前**拦住，否则就是先花钱再拒绝"*。

### 6.3 记账必须完整（含失败与断流）

`llm_call_log.status` 取值：`ok | timeout | parse_fail | budget_exceeded | aborted | stream_broken`

★**`stream_broken` 也要记账** —— Histrategy 的教训，代码注释原话：
> "the LLM call was STILL BILLED, so record what we consumed… Without this the call silently disappears from llm_call_log — **an accounting gap**"

客户端断开时上游已经计费，不记就是成本黑洞。

### 6.4 usage 拿不到就估算

流式调用带 `stream_options: {include_usage: true}` 取真实 usage；provider 拒绝则退回估算。
★估算口径**中文按 chars/2**（不是 Histrategy 的 chars/4，那是英文口径，会低估中文提示词一倍）。

### 6.5 复现本文数字的命令

```bash
# 提示词体积实测（本文 §2.1 的数据来源）
node --experimental-strip-types tools/measure-prompt.ts   # 输出 system/user/JSON 对照表
node --experimental-strip-types tools/measure-prompt.ts aria  # 架空剧本

# 全部成本相关闸门
node --experimental-strip-types --test tests/deterministic/ai-layer.test.ts

# 真实模型端到端（无 key 自动 skip；验协议一致性，不评模型水平）
LLM_API_KEY=sk-... LLM_MODEL=deepseek-chat npm run test:llm
```

真实端到端验的是：建议里的 `legalActionId` **必须**来自引擎的合法动作空间、`snapshotDigest` 必须对得上当前局面、
每次调用（含失败）都要有 `tokenUsed` 记账、人类席位在 `autoCommit=false` 下绝不自动提交。
它**不**断言"建议是否聪明"——那是模型能力，不是协议问题。

| 5 | 系统提示词缓存（provider 侧） | 输入单价 ↓ 至 1/10 | DeepSeek 自动缓存命中 | ⚠️ 依赖 provider |
| 6 | 叙事移出关键路径 + 用小模型 | 延迟 ↓ + 单价 ↓ | `resolveTurn` 与 `generateNarratives` 分离 | ✅ |
| 7 | 建议预计算缓存（点选零延迟） | 交互延迟 ↓ | 架构文档 §3.2 已设计 | ⏳ 待房间层接线 |
| 8 | 预算闸前置 + 降级 | 上限封顶 | `src/ai/advisor.ts` | ✅ |
| 9 | 单飞 + 在途合并 | 防重复调用 | `AiAdvisor.request()` | ✅ |
| 10 | 只对 408/425/429/5xx 重试 | 防烧钱重试 | `src/ai/llm-client.ts` | ✅ |

**第 5 条值得单独说**：系统提示词 888 tokens 在同一席位的连续回合里**几乎完全相同**
（只有回合号、里程碑状态、往局教训会变）。如果 provider 支持提示词缓存（DeepSeek 支持），
命中部分的输入单价通常降到 1/10。这意味着 §5.3 表里配置 A 的 ¥1.38 还能再降到 **~¥0.9**。
要吃到这个红利，**系统提示词必须稳定前缀 + 变化部分放尾部**——`renderSystemPrompt()` 的结构已经按这个排了
（角色/剧本/纪律在前，里程碑与往局教训在后）。

## 8. 已知取舍与未做的事

诚实列出，避免过度承诺：

1. **没做提示词缓存的主动管理**。只是把结构排成"稳定前缀 + 变化尾部"以**利于** provider 自动命中，
   没有实现显式的 cache-control 标记（DeepSeek 目前也不需要）。
2. **没做跨局经验的向量化检索**。`ai_memory` 表按 OpenRA-RL 的 `memory.json` 模式做纯结构化存取
   （最近 3 局 + 最佳 2 胜），不引入向量库——那是 OpenArma 的重型路线（pgvector + Qdrant），我们砍掉了。
3. **narrative 的 ~800 输入 tokens 是估算而非实测**，因为事实清单的渲染依赖房间层组装的回合事件，
   该链路尚在集成中。§5.2 的配置 A/B 数字因此有 ±15% 的误差带。
4. **单价表是假设值**。本文给的是公式与敏感性区间，换 provider 只需替换单价重算。
5. **没做按房间的动态模型降级**（例如预算过半就自动切 flash 档）。目前是"超限即降级为启发式"的一刀切。
   这是可加的，`scenario.json` 的 `budget.onExceed` 已经预留了字符串枚举位。
