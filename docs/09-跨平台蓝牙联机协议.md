# 跨平台蓝牙联机协议（Android / iOS / HarmonyOS）

## 0. 调研结论（2026-11-16）

**没有**现成的「iOS + Android + HarmonyOS 三端蓝牙联机（多人游戏主机/客机）」方案可直接用：

| 候选 | 平台 | 为什么不够 |
|---|---|---|
| `marsel-code/blue-falcon` | Android / iOS / macOS / RaspberryPi / JS（Kotlin Multiplatform） | 只有 **BLE Central**（扫描/连接/读写特征值），没有 GATT Server / 广播角色；且不支持 HarmonyOS。最后一次实质更新 2025-06。 |
| `flutter_blue_plus_ohos` | Android / iOS / OHOS | 同样是 **Central-only** 的 BLE 调试库；不支持广播、GATT Server，也没有多人房间/信道语义。 |
| `react-native-ble-plx` | Android / iOS | 同样 Central-only；HarmonyOS 需要社区 fork，不能三端一套。 |
| Apple `MultipeerConnectivity` | 仅 iOS/macOS | 不是三端。 |
| Google `Nearby Connections` | Android/iOS | 无 HarmonyOS，且无法与 iOS 系统级互通到同一套 GATT 语义。 |
| **当前 APK 的 SPP/RFCOMM** | 仅 Android | iOS 必须 MFi 认证才能用经典蓝牙 SPP；普通 App 只能用 CoreBluetooth（BLE GATT）。HarmonyOS 也不保证对端 SPP 互通。 |

结论：**用 BLE GATT 自己做传输层**。游戏核心（JS `uno-core.bundle.js`）本来就是 transport-agnostic：它只依赖「字节流 + 4 字节长度前缀 + JSON」，把它搬到你手机上是纯透传，不需要改规则。

## 1. 不动的部分（三端共用同一份 `assets/www`）

JS 侧看到的原生桥**名字与方法名保持不变**：

```

window.UnoBtAndroid.getDeviceName()      -> string
window.UnoBtAndroid.getRoomUrl()         -> string | null
window.UnoBtAndroid.getGame()            -> string

window.UnoBtAndroid.findAndConnect() / disconnect()

window.UnoBtAndroid.sendToHost(b64)
window.UnoBtAndroid.llmInfo() / llmConfigure(baseUrl, model, apiKey) / llmClear()
window.UnoBtAndroid.llmChat(requestId, messagesJson)
window.UnoBtAndroid.civLlmChat(requestId, messagesJson, maxTokens, timeoutMs)
```

原生 → JS 的回调也保持不变：

```
window.UnoBtOnJoin(channelId)
window.UnoBtOnData(channelId, base64)
window.UnoBtOnDisconnect(channelId)
window.UnoBtOnConnected()
window.UnoBtOnStatus(text)
window.UnoBtOnLlmResponse(requestId, {ok:true,text} | {ok:false,error})
```

> iOS 的 `WKWebView` 没有 Android 那种同步注入对象。做法：在 `WKUserContentController` 里注册名为 `UnoBtAndroid` 的 messageHandler，再用 **document start 脚本**注入一个同名 JS 对象：同步 getter 从预注入的 `window.__unoBtConfig` 读，其它方法 `postMessage({method,args})`。原生回调仍走 `evaluateJavaScript("window.UnoBtOnData(...)")`。HarmonyOS 的 WebView 用 `javaScriptProxy` 注入同名对象（它支持同步方法），与 Android 几乎一致。

## 2. BLE GATT 契约

### 2.1 UUID

| 项 | UUID |
|---|---|
| Service | `a6b1c0de-0001-4f52-9a11-0a1b2c3d4e5f` |
| RX Characteristic（客机写 → 主机） | `a6b1c0de-0002-4f52-9a11-0a1b2c3d4e5f` |
| TX Characteristic（主机通知 → 客机） | `a6b1c0de-0003-4f52-9a11-0a1b2c3d4e5f` |

- 主机（host）= GATT **Peripheral / Server**：广播 Service UUID，accept 多个 Central。
- 客机（guest）= GATT **Central / Client**：扫描 Service UUID，连接后订阅 TX notify。
- 广播名称建议 `桌游-<设备名>`，扫描按 Service UUID 过滤，不靠名字。

### 2.2 信道（channelId）

- 主机每 accept 一个 Central，分配一个递增 `channelId`（从 1 开始）；断开后**不复用**编号（与现有 SPP `BluetoothService` 一致）。
- 客机永远是 `channelId = 0`。
- 主机发送：`sendToChannel(id, b64)` → 找到该 id 对应的 Central → TX notify 分片。
- 客机发送：`sendToHost(b64)` → RX write 分片。
- 主机收到 RX write：按发起写入的 Central 反查 channelId，回调 `UnoBtOnData(channelId, b64)`。
- 客机收到 TX notify：回调 `UnoBtOnData(0, b64)`。

### 2.3 分片与保序

- BLE ATT 默认 MTU 23（有效 20B）；Android/HarmonyOS 可协商到 512，iOS 自动协商（常见 185）。
- 每片负载 ≤ `min(mtu - 3, 512)`；**必须串行发送**（一条未回调前不发下一条），否则会乱序。
- 分片后的字节流直接喂给 JS 的 `FrameDecoder`：它本来就接受任意大小的 chunk（见 `bt-online/protocol.js`）。
- 建议原生层用「每连接的发送队列 + 发送完成回调再出队」；不要并发写同一个特征值。
- 写入类型优先 `WriteWithoutResponse`（吞吐好）；iOS 若报 `Writing is not permitted`，回退 `WriteWithResponse`。

### 2.4 生命周期与错误文案

| 事件 | 主机 | 客机 |
|---|---|---|
| 就绪 | 广播成功 → `UnoBtOnStatus("等待玩家连接…")` | 发现服务并开启 notify → `UnoBtOnConnected()` |
| 有人加入 | Central 订阅 TX → `UnoBtOnJoin(channelId)` | — |
| 断开 | `UnoBtOnDisconnect(channelId)` | `UnoBtOnStatus("与主机断开连接")` |
| 蓝牙未开 | `UnoBtOnStatus("请先开启蓝牙，…")` | 同 |
| 权限不足 | `UnoBtOnStatus("需要蓝牙权限…")` | 同 |

LLM 相关的桥方法与回调**保持完全一样**，只是原生实现从 `HttpURLConnection` 换成 `URLSession`（iOS）/ `@ohos.net.http`（HarmonyOS）。Key 仍只在进程内存，不落盘、不进 WebView 本地存储。

### 4.1 静态一致性闸门

`tests/deterministic/ble-protocol.test.ts`（零依赖，5 条）在 `npm run verify` 中执行，断言：
1. 三端源码中的三个 BLE UUID 与本协议文档一致；
2. iOS `NativeBridge`、鸿蒙 `javaScriptProxy`、Android `BtJsBridge` 的 16 个方法名一致；
3. 六个 `UnoBtOn*` 回调名与 WebView 资源一致；
4. `clients/sync-assets.mjs` 覆盖三端目标目录；
5. iOS / 鸿蒙不出现 `SPP/RFCOMM`（避免撞上 Apple MFi 限制）。
