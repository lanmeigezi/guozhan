# 将领系统与史料依据（2026-11-15）

## 0. 一句话

给「戰國七雄（完整版）」加入**史料可考的将领**：将领挂在**部队**上，每人 2–3 条带《史记》/《战国策》出处的特征，映射成**确定性乘数**；只加规则、不加随机、不让 LLM 造人。

## 1. 启用范围（重要）

| 剧本 | 将领 | 说明 |
|---|---|---|
| `warring-states-full` | ✅ 16 位 | 真实七雄 + 史实地图 + 完整模块集，`scenario.json` 显式声明 `knowledge.generalsFile` 并在 `moduleOrder` 末尾加 `generals` |
| `warring-states`（经典） | ❌ | **项目刻意的旧存档兼容基线**：`scenario-iron-front.test.ts` 把它的 `contentHash` 与 `behaviorFingerprint=36775` 逐字锁死，`warring-states-full` 的剧本描述也写明「旧『戰國七雄（经典）』保留最小模块集用于兼容旧存档」。给它加模块会顶掉所有旧档，故保持原样 |
| `grand-front` / `aria` / `frontier` / `iron-front` | ❌ | 随机超大陆或虚构势力，套战国名将会时空错位；且「不要凭空创造武将」 |
| `random-front*` / 其余 | ❌ | 行为与 contentHash 逐字不变 |

> 用户最初选的是「战国两剧本」。实现时按上面这条硬约束收窄到 `warring-states-full` 一个；经典版要玩将领，请新建剧本目录（复制 full 的 `scenario.json` 换个 `meta.id`），不要改兼容基线。

## 2. 史料纪律

`docs/research/02-histrategy.md` 记下了 Histrategy 的数值禁区：

> ❌ 不要凭空创造新的武将或势力
> ❌ 不要让已死亡的人物复活

本项目的落点：

1. 名册是**不可变内容**（`WorldConfig.generals`），随 `contentHash` 一起参与存档身份校验；改一个数字、加一个虚构人物都会让旧档 `verifyIdentity` fail-closed。
2. 只收史料可考人物；`traits[].source` 是必填项，装载器 fail-fast 校验。
3. 将领随建制走：部队被歼 / 被合并即退场，征兵与分兵产生的新部队**不带将领**，已退场将领无法再任命（`GENERAL_NOT_IN_SERVICE`）。
4. LLM 只能看到名册与合法动作 id，不能提交名册外的 `generalId`（`UNKNOWN_GENERAL`）。

**引文口径**：`traits[].text` 是史书记载的**概括**，不是逐字引文；个别传世语句（如「两鼠斗于穴中，将勇者胜」「批亢捣虚」）按通行读法标注。出处给到篇名，便于核查，**未做版本校勘 / 今古文比对**。韩国将才可确证的记载远少于六国，只收 1 位并在 `source` 里明写「记载稀薄」，特征取「赴援守御」而非虚夸战功。

### 数值维度（全部确定性，无随机触发）

| 字段 | 口径 | 范围 |
|---|---|---|
| `attackMultiplier` | 该部队作攻方时的战力乘数 | 0.5–1.5 |
| `defenseMultiplier` | 该部队作守方时的战力乘数 | 0.5–1.5 |
| `siegeMultiplier` | **仅攻方**、目标 `fortLevel > 0` 时额外乘数 | 1–1.5 |
| `moraleMultiplier` | 该部队士气项乘数（作用于战力，**不改持久化民心**） | 0.8–1.3 |
| `unitAffinity` | 带指定兵种时额外乘数 | 1–1.5 |
| `movementBonus` | 该部队本回合移动力加数（整数点） | 0–2 |

单一真源：`src/core/state.ts` 的 `generalCombatMultiplier()` / `generalMovementBudget()`。实战 `computePower()`、UI 预估 `sumPower()/estimateBattle()`、合法动作枚举 `legal.ts`、结算 `movement.ts` 全部调用同一函数，避免「UI 说能到、结算说到不了」。乘数 `Math.round(v*10000)/10000`，同种子逐位可复现。

**攻城乘数只在攻方生效**：守方永远不吃 `siegeMultiplier`，避免「守坚城也算攻城」。

## 4. 状态与生命周期

- `UnitState.generalId?: GeneralId` —— 唯一进权威状态的将领字段。
- 开局由 `config-loader.ts` 按 `assignedTo` 绑定，装载期 fail-fast 校验「部队存在 / 将帅同国 / 不重复指派」。
- `set_unit_general` 变更会**先从其它部队摘掉同一个 id**，保证一名将领只带一军。
- `destroy_unit` 不迁移 `generalId`：将领随建制消失且不复活。
- 分兵（`split_unit`）产生的新部队不带将领；合兵（`merge_units`）以目标建制为准，被合并部队的将领随建制退场。
- 征兵（`spawn_unit`）不产生将领。

## 5. 命令与拒绝码

`assign_general { generalId, unitId }` —— 把本势力**在编**将领改派到另一支己方「无将」部队。同名将领调回自己当前部队是幂等无操作。

| 拒绝码 | 触发 |
|---|---|
| `UNKNOWN_GENERAL` | 名册里没有这个人 / 剧本未启用将领 |
| `GENERAL_NOT_OWNED` | 将领属于别国 |
| `GENERAL_NOT_IN_SERVICE` | 已随原建制退场，不能复活 |
| `MALFORMED_PAYLOAD` | 目标部队已由别的将领统率（请先把那位调走） |
| `UNKNOWN_UNIT` / `UNIT_NOT_OWNED` | 目标部队不存在 / 不属于你 |

`general_assigned` 事件可见性为 `owner`（不把部署广播给敌国）。

## 6. 战报证据

`combat_resolved.evidence.generals`：

```
attacker: [{ generalId, name, unitId, multiplier }]
defender: [{ generalId, name, unitId, multiplier }]
attackerMultiplier / defenderMultiplier   // 按兵力加权平均
```

拿到不可变名册 + 这两组数字即可复算将领对战力的贡献；战斗时间线 UI 显示「攻方将领 白起 ×1.239」。未启用将领系统的剧本 / 旧事件回放没有这个字段。

## 7. 迷雾

- `Snapshot.generalRoster` 是**公开史料**（姓名、称号、国别、出处、特征、数值），**不含部署**。
- 谁带哪支部队只出现在 `ProjectedRegion.stacks[].generalId/generalName`，而 `stacks` 本来就要过 `canSeeStacks()`；未侦察的敌国区域不下发将领部署。
- 右栏「史料将领」折叠面板按「我方 / 列国」分组，部署反查只用当前快照里可见的 stacks，看不见就显示「部署未明」。

## 8. 兼容与哈希

- `knowledge.generalsFile` 与 `moduleOrder: [..., "generals"]` 都要显式声明，缺一个都不启用。
- `hashInput['generals'] = 名册`：改名册会让 `warring-states-full` 的 contentHash 变化，旧档 fail-closed（预期行为）。
- 新模块 `generals` 只写 `units.generalId` 这一片新切片，**与任何既有模块无写重叠**；战力/行军是纯查询，不改状态。
- 未声明的剧本不读文件、不往 `WorldConfig` 塞字段、不下发 `generalRoster`，contentHash 与 behaviorFingerprint 逐字不变。

## 10. 以后怎么改

- **调数值**：只动 `config/scenarios/warring-states/generals.json` 的 `effects`，重跑 `npm run verify`。
- **加人物**：必须给 `source` 与 `traits[].source`，且 `factionId` / `assignedTo` 在本剧本中存在；**不要虚构**，史料不足就别加。
- **换剧本**：复制 `warring-states-full/scenario.json` 到新目录，改 `meta.id`，`generalsFile` 指向同一份名册；不要动经典版。
- **加维度**（如「战后动乱」）：先想清楚它会不会让 `generals` 模块写已有切片——一旦写 `regions.unrest` 就要在 `KNOWN_WRITE_OVERLAPS` 里登记，别悄悄制造写重叠。
